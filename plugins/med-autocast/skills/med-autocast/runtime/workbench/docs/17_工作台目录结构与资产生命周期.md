# 工作台目录结构与资产生命周期

更新：2026-09-28。本文件定义工作台的目录职责、生产交接和历史兼容边界。它与 `workbench.yaml`、系列登记和单集制作单一起决定文件放在哪里；不以目录名称推断审核通过。

## 1. 唯一入口与职责

工作台根目录是方法、档案、内容、制作和交付的容器。每类文件只有一个当前权威层：

```text
科普视频/
├── docs/                 方法、SOP、外部方法落地和本机记录
├── .agents/skills/       专业岗位入口，只保存决策与路由
├── content/              医学事实、患者问题地图、系列计划、旁白和故事包
├── profiles/             作者/医生、品牌、声线和部署档案
├── backends/             后端能力合同和安装入口，不放运行输出
├── assets/               跨篇复用且已登记来源的稳定资产
├── productions/          正在制作的系列与单集，含分镜、透明素材、候选和 QA
├── publish/              已整理的审看/交付包，只复制当前明确版本
├── deliveries/           内部交接和历史交付记录，不作为制作权威
├── archive/              只读历史候选、旧原型和被否决版本
├── work/                 可恢复的运行态、回执、浏览器审片和实验
├── output/               工具生成的批量输出，需经人工挑选后才能入库
├── tmp/                  可重建的临时文件，不得作为交付来源
├── scripts/              工作台工具
└── templates/            新作者、新系列和单集的待填写骨架
```

`docs/` 说明怎么做，Skill 决定当前由谁做，档案决定用谁的身份/声线/品牌，`content/` 决定医学含义，`productions/` 记录这一次实际做了什么，`publish/` 只投影已选版本。通用 Skill 不写死 Dr.咩；系列品牌从作者/系列档案读取。

## 2. 新系列与新单集的标准结构

新系列使用 `productions/<series_id>/<episode_id>/`。旧的 `productions/01_...` 等扁平路径是历史兼容布局，不在本轮强制搬迁：

```text
content/<topic_id>/
├── 00_brief.md
├── 01_sources.md
├── 02_fact_library.yaml
├── 03_patient_question_map.md
├── 04_series_plan.md
├── 05_visual_library.yaml
├── 06_release_catalog.yaml
└── episodes/<episode_id>/
    ├── 00_episode_brief.md
    ├── 01_narration.md
    ├── 02_visual_treatment.md
    └── 03_story_package.yaml

productions/<series_id>/<episode_id>/
├── 00_production_readme.md
├── preproduction/        视觉导演稿、beat grid、分镜、episode_blueprint
├── animatic/             粗动态分镜和导演审片记录
├── assets/               本集素材清单、透明分层和来源/许可回执
├── animation/            JS/SVG/Canvas 源码、字体和项目配置
├── audio/                IndexTTS/Edge、SRT、BGM、音效和合成回执
├── candidates/           可审候选，不等于 final
├── qa/                   静帧、动作 strip、字幕安全区和视听/医学审核
├── final/                只有通过相应门禁的当前技术母版
└── archive/              本集被替换的旧版本和修订原因
```

内容文件只放医学语义和交接；导演稿和分镜放 `preproduction/`；大场景图只能作背景或风格帧，能独立运动的医学主体、情境物件、遮挡片、阴影和文字层放 `assets/` 并在清单中登记。JS 代码读同一份时间轴，先过粗动态分镜再进入 `animation/`，这样不会把旁白逐句变成卡片。

## 3. 资产状态与流转

```text
外部检索/ImageGen/作者资产
  -> assets 或单集 assets/（来源、许可、提示词、医学边界）
  -> preproduction/ 与 animatic/（导演证明观看任务）
  -> animation/ 与 candidates/（可运行候选）
  -> qa/（逐镜、连续运动、字幕、声音、医学分别记录）
  -> final/（当前合格母版）
  -> publish/（审看包或正式交付投影）
```

文件存在、浏览器能渲染、技术 QA 通过、联系表好看，都只证明各自一层。素材准入、动作叙事、完整听感、医学复核和公开发布资格必须保留独立状态。旧候选不覆盖新候选；被否决素材登记原因后留在 `archive/` 或单集 `candidates-rejected/`。

## 4. 运行态和历史兼容

- `work/` 保存可恢复的任务状态、后端回执、切点审片和实验；其中的文件可以被内容或制作单引用，因此清理前必须先检索引用。
- `output/` 保存工具批量生成的图像、Playwright 截图和联系表。人工认可的可复用资产要复制到 `assets/`，并补来源与用途；不能把 `output/` 当作发布来源。
- `tmp/` 只放可重建中间文件；完成后可清理，但先确认没有制作单、QA 或回执引用。
- `deliveries/` 是交接记录和历史审看包，`publish/` 才是当前发布入口；两者都不能反向成为新的制作权威。
- `archive/early-prototypes/`、被否决的 JS 样片和旧 H3 候选只读保留，用于复盘，不作为默认风格或质量证据。
- 当前垂体瘤的扁平单集目录、旧 QA 目录和绝对路径继续有效；新建或下一轮返修使用本节的系列/单集结构，逐步迁移而不是一次性重命名。

## 5. 目录变更规则

移动或归档前依次检查：

1. `rg` 检索绝对路径、相对路径、制作单、manifest、README 和脚本引用；
2. 确认没有仍在写入的渲染、TTS、浏览器或打包进程；
3. 保留原文件名、回执和修订关系，必要时在原位置留下 README 指针；
4. 移动后运行 `workbench_config validate`、受影响的脚本检查和链接回读；
5. 只有用户明确要求清理且已有可恢复副本时才删除原路径。

目录重组的目标是减少新工作的认知成本，而不是把历史资产伪装成新结构。任何新系列都应从模板创建自己的 `content_root`、`production_root`、QA 和发布入口，不共享另一系列的状态文件。
