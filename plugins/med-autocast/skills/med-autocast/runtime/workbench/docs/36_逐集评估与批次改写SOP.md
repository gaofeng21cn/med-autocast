# 逐集评估与批次改写 SOP

## 为什么不能批量重渲染

89 集曾做过一次"相机语法"批量升级：给每个疾病系列不同的构图、景别和推移速度，然后重渲染全部 89 集。核对源码后确认这轮没有改善动画本体——垂体瘤 12 集一行未改，其余 77 集只换了 `camera`，场景仍是物件并排摆好然后停住。

结论：批量重渲染不等于优化。优化必须落在镜头实现上，而且要能逐集说明改了什么。

## 评估先行

`scripts/evaluate_episodes.py` 从每集自身的 TypeScript 与 `score.json` 提取代码事实：

- 动作库与编排模式的调用密度（`actions.ts` 的纸件动作 + `patterns.ts` 的编排骨架）
- 纸件容器与固定件使用量
- 机位是否真的在运动（区分动态与固定表达式）
- 画内文字量
- 舞台数量
- 动作时点是否由 `beat.events` 驱动

判定：<55 需重写，55–75 需升级，>75 可保持。

**评估器口径本身要复核。** 早期版本只统计 `actions.ts` 调用，把所有用 `patterns.ts` 编排的镜头判成"动作密度 0"，分数虚低约 30 分。改口径后同一集从 46.7 变 88.0。凡是评估结果与肉眼观感冲突，先怀疑测量口径。

## 批次划分：按杠杆，不按系列

一次重写能带动多少集，决定优先级。基线（2026-10-13）：

| 批次 | 范围 | 集数 | 起始均分 |
| --- | --- | --- | --- |
| W1 | 高血压 + 科学减重 + 血脂 | 25 | 39.3 |
| W2 | 痛风 + 甲亢 + 多囊 + 肾病 + 桥本 + 乳腺 | 41 | 48.0 |
| W3 | 糖尿病 04（独立工厂） | 1 | 13.7 |
| W4 | 垂体瘤（每集独立导演稿） | 12 | 约 28 |

共用工厂的系列一次改写全部受益；独立导演稿的系列必须逐集重做，套用共享模式反而抹掉个性。

## 每批固定流程

1. 取改写前基线
2. 重写工厂或分镜，时序走 `kit/patterns.ts`，画面按导演意图重画
3. 全集 `npm run build`
4. **抽一集 render，抽帧看原尺寸**——不目视确认不得批量 render
5. 全批 `render` → `package`
6. 复跑评估器确认分数上升
7. 更新逐集报告状态列

## 目视确认要抓什么

批量改写最常见的失败是"代码对了、画面退步"。以下四类必须逐帧看：

- **空白占位方块**：新增的纸片如果没有内容，会读成素材缺失。这是反复出现的真实缺陷，宁可不加这张纸。
- **文字打架**：新加的标签压住原有标题或记录线，叠第二张纸通常比写在原地更糟。
- **动作方向**：物件应该从画外飞入落到工位，不是原地淡入。
- **接触阴影**：落桌、落盘、夹合都要有阴影，否则接触读成重叠。

## 已验证的改写手法

- **一次读数**：设备飞入 → 读数随事件点亮 → 记录本飞入落位 → 笔迹写在页上 → 接触阴影。全程由 `beat.events` 驱动时点。
- **三张读数叠放**：每张依次滑入并轻微错位，最后夹子合拢——"重复"变成可数的东西。
- **两份记录对照**：两张纸被推到一起、对齐、夹合成一个判断，而不是并排放。
- **上桌动作**：食物从盘外飞入盘中，落点有阴影；替换时被换下的原件移向桌缘。
- **纸页翻过**：旧页翻起并压在下面，新页落下，时间差可见。
