# 逐集评估与独立改写 SOP

## 评估先行，但逐集改写

`scripts/evaluate_episodes.py` 从每集自身的 TypeScript 与 `score.json` 提取代码事实：

- 动作库与编排模式的调用密度（`actions.ts` 的纸件动作 + `patterns.ts` 的编排骨架）
- 纸件容器与固定件使用量
- 机位是否真的在运动（区分动态与固定表达式）
- 画内文字量
- 舞台数量
- 动作时点是否由 `beat.events` 驱动

判定：<55 需重写，55–75 需升级，>75 可保持。

**评估器口径本身要复核。** 早期版本只统计 `actions.ts` 调用，把所有用 `patterns.ts` 编排的镜头判成动作密度 0，分数虚低约 30 分。改口径后同一集从 46.7 变 88.0。凡是评估结果与肉眼观感冲突，先怀疑测量口径。

## 两条历史教训（写在这里就是为了不再犯）

1. **批量重渲染不等于优化。** 89 集曾做过一次「相机语法」批量升级：给每个疾病系列不同的构图、景别和推移速度，然后重渲染全部 89 集。核对源码后确认这轮没有改善动画本体——垂体瘤 12 集一行未改，其余 77 集只换了 `camera`，场景仍是物件并排摆好然后停住。
2. **共用工厂不是效率。** 76 集共用 3 个渲染工厂后，「一次改写全部受益」的批处理思路看似高效，实际把 89 集压成 11 集的导演稿。系列级工厂从一开始就不该存在（见 `docs/34_逐集独立导演与系列资产分层SOP.md`）。

## 批次只用于排期与验收，不用于共享实现

批次划分的作用是安排渲染与目视验收的人力，以及记录进度，**不是**让一组集数共用一份镜头代码。每一集都要：

1. 取本集基线（评估分 + 目视记录）
2. 读本集 `episode_stories.yaml` 的 beats 与 directing
3. 独立撰写本集 `episodeshots.ts`（5 镜各自的空间、动作因果、相机）
4. 重写本集 `scene_directions.json`（只含本集镜头 + 本集 intent）
5. `build` → `render` → 抽帧目视（进入帧、动作极值、接触落点、切出帧）
6. `package` 发布
7. 更新逐集报告：改了什么、依据哪条 beat、还剩什么质量债

## 目视确认要抓什么

- **空白占位方块**：新增的纸片如果没有内容，会读成素材缺失。这是反复出现的真实缺陷，宁可不加这张纸。
- **文字打架**：新加的标签压住原有标题或记录线，叠第二张纸通常比写在原地更糟。
- **动作方向**：物件应该从画外飞入落到工位，不是原地淡入。
- **接触阴影**：落桌、落盘、夹合都要有阴影，否则接触读成重叠。
- **实景照片背景**：环境板若是照片，与纸拼贴主体属于两种媒介，必须换成纸景板或做足纸化处理（见 `docs/35`）。
- **无意义大色块**：画面里的大面积色块如果只是文字底板又没有和物件对齐，删掉比留着好。

## 已验证的导演手法（可复用为原语，不是可复用为镜头）

- **一次读数**：设备飞入 → 读数随事件点亮 → 记录本飞入落位 → 笔迹写在页上 → 接触阴影。全程由 `beat.events` 驱动时点。
- **三张读数叠放**：每张依次滑入并轻微错位，最后夹子合拢——重复变成可数的东西。
- **两份记录对照**：两张纸被推到一起、对齐、夹合成一个判断，而不是并排放。
- **进入-操作-反应-落定**：见 `kit/patterns.ts` 的 `arc()`。本集从哪到哪、为什么、什么时候反应，由导演决定。

这些是手法库。每一集用哪几个、怎么排、填什么物件，仍由本集导演决定。
